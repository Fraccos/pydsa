Binary Search: From Sorted Arrays to Search-on-Answer

A practical, NeetCode-inspired study guide for SDE mid-level interviews. Binary search is not about sorted arrays — it's about monotonicity. Master the templates here and you unlock a whole family of problems that never mention sorting at all.

Includes embedded diagrams, Python examples, complexity analysis, a study roadmap with direct LeetCode links, and your first practice problem. This file is self-contained and works offline. Companion guide: Binary Search Trees (binary search made into a data structure).

1. What is binary search?

Binary search finds an answer in a search space by repeatedly asking a yes/no question about the middle and discarding half the space. On a sorted array, the question is "is the middle element before or after my target?" — and each probe eliminates half of what remains, giving O(log n) probes instead of O(n).

  • The precondition that actually matters: monotonicity. If some property is false, false, …, false, true, true, … — binary search finds the boundary. "Sorted array" is just the most common instance (the property: "element ≤ target").
  • The loop invariant: the answer, if it exists, is always inside [lo, hi]. Every iteration must preserve this — and make progress — by discarding half.
  • Logarithmic cost: log₂(1,000,000) ≈ 20. This is why "can I binary-search it?" is the first question to ask on any large search space.
  • Bug-proneness is the catch: off-by-one errors, infinite loops on two-element ranges, and wrong boundary handling. The cure is choosing one template and understanding its invariant (Section 5, Pattern 1).

2. Binary search in Python (and bisect)

def binary_search(nums, target):       # LeetCode 704
    lo, hi = 0, len(nums) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if nums[mid] == target:
            return mid
        elif nums[mid] < target:
            lo = mid + 1               # discard mid and everything left
        else:
            hi = mid - 1               # discard mid and everything right
    return -1

Notes that matter in interviews:

  • mid = (lo + hi) // 2 is safe in Python (arbitrary-precision ints). In C/Java you'd write lo + (hi - lo) // 2 to avoid overflow — worth mentioning as a known detail.
  • The loop runs while the range is non-empty (lo <= hi) and discards mid itself each time — that pairing is what guarantees termination. Mixing conventions from different templates is the classic infinite-loop bug.

For boundary searches, the standard library has done the tricky part since 3.x — and interviewers accept it unless they explicitly want the manual version:

from bisect import bisect_left, bisect_right, insort

nums = [1, 3, 3, 3, 7]
bisect_left(nums, 3)     # 1 — leftmost position where 3 could be inserted
bisect_right(nums, 3)    # 4 — just past the rightmost 3
bisect_left(nums, 4)     # 4 — first element greater than 4 (ceiling)

# count of 3s = bisect_right - bisect_left; "does 3 exist" = nums[bisect_left] == 3
insort(nums, 5)          # O(n) insert (shift) at the O(log n) found position

3. Binary search vs. the rest of the series

Linear scan

O(n), no preconditions. Fine for small n; the thing to beat.

Useful for: unsorted data when sorting isn't free.

Balanced BST

Binary search as a data structure — O(log n) search plus O(log n) insert/delete while staying searchable.

Useful for: dynamic sorted data. See the BST guide.

Heap

O(1) peek at one extreme — but finding an arbitrary value is O(n). Binary search needs the order a heap hides.

Useful for: when only the extreme matters. See the Heaps guide.

The universal test: can you write a predicate feasible(x) that, once true, stays true for all larger (or smaller) x? Then binary search over x finds the boundary in O(log(range) × cost of predicate). If you can't name the monotonic property, slow down — you're probably not looking at a binary search problem.

5. Four core interview patterns

Pattern 1 — The boundary template (leftmost true)

Most real problems aren't "find exact value" but "find the first index where a condition holds". One template covers them all — including exact-match and insertion-position problems:

def leftmost(nums, target):            # first index with nums[i] >= target
    lo, hi = 0, len(nums)              # hi is EXCLUSIVE: search space [lo, hi)
    while lo < hi:
        mid = (lo + hi) // 2
        if nums[mid] < target:
            lo = mid + 1               # mid is too small — and so is everything left
        else:
            hi = mid                   # mid qualifies — but an earlier one may exist
    return lo                          # lo == hi == first qualifying index

# first index with nums[i] > target  →  same loop with  nums[mid] <= target
Why this template kills off-by-one bugs: the search space is half-open [lo, hi) and hi starts at len(nums) — a legal answer even if every element qualifies. The loop ends when lo == hi, so there is exactly one exit state, and lo is the boundary. Never re-derive this in an interview; write the invariant, then trust it: "everything left of lo is false, everything from hi on is true."

Common problems: 35 Search Insert Position, 34 First and Last Position (run it twice), 278 First Bad Version (the predicate is an API call).

Pattern 2 — Sorted-but-mangled arrays (rotated, peaks)

Rotation and peaks break global sortedness but keep a local sorted half, which is enough to decide which side to discard:

def search_rotated(nums, target):      # LeetCode 33
    lo, hi = 0, len(nums) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if nums[mid] == target:
            return mid
        if nums[lo] <= nums[mid]:      # LEFT half [lo..mid] is sorted —
            if nums[lo] <= target < nums[mid]:
                hi = mid - 1           # target in the sorted half
            else:
                lo = mid + 1
        else:                          # RIGHT half [mid..hi] is sorted
            if nums[mid] < target <= nums[hi]:
                lo = mid + 1
            else:
                hi = mid - 1
    return -1

The discipline: at each step, identify which half is sorted, then check whether the target lies inside that half's value range. Variants: minimum of a rotated array (153 — compare nums[mid] to nums[hi]), peak finding (162 — walk toward the higher neighbor), 2-D matrix (74 — binary search over m·n treated as one array, or two searches).

Pattern 3 — Binary search on the answer (the big unlock)

The search space doesn't have to be an array at all. If the answer itself is a number whose feasibility is monotonic, binary search over candidate answers:

def min_eating_speed(piles, h):        # LeetCode 875: Koko Eating Bananas
    def hours_needed(speed):
        return sum((pile + speed - 1) // speed for pile in piles)

    lo, hi = 1, max(piles)
    while lo < hi:                     # search space: possible speeds
        mid = (lo + hi) // 2
        if hours_needed(mid) <= h:     # feasible — maybe a slower speed works
            hi = mid
        else:                          # too slow — need a bigger speed
            lo = mid + 1
    return lo

Why it works: if Koko can finish at speed s, she can finish at any speed above s — feasibility is monotonic in the answer. So the answer space looks like false false … false true … true, and the loop above finds its left edge. Cost: O(n · log(max(piles))) — log of the value range, times one linear scan per probe.

Pattern 4 — bisect as a building block

Design problems often reduce to "keep a sorted log and query boundaries". 981 Time Based Key-Value Store: per key, keep parallel lists of timestamps and values (timestamps are naturally increasing); get is bisect_right minus one:

import bisect

class TimeMap:
    def __init__(self):
        self.times = {}     # key -> [timestamps, increasing]
        self.vals = {}      # key -> [values, aligned with times]

    def set(self, key: str, value: str, timestamp: int) -> None:
        self.times.setdefault(key, []).append(timestamp)
        self.vals.setdefault(key, []).append(value)

    def get(self, key: str, timestamp: int) -> str:
        i = bisect.bisect_right(self.times.get(key, []), timestamp)
        return self.vals[key][i - 1] if i else ""

The habit: when a problem says "largest timestamp ≤ t" or "how many elements ≤ t", translate directly to bisect_right/bisect_left arithmetic instead of hand-rolling a loop. The cost is O(log n) per query, O(1) amortized per insert-at-end.

7. Interview checklist

  1. Monotonicity: What exactly is false-then-true (or increasing)? Can I state the predicate in one sentence?
  2. Template: Half-open [lo, hi) with hi = mid, or closed [lo, hi] with mid ± 1? Pick one and don't mix.
  3. Termination: Does every path strictly shrink the search space? (The lo = mid without +1 mistake is the classic infinite loop.)
  4. Half-open discipline: hi exclusive means initial hi = len(nums) and exit when lo == hi.
  5. Return value: Is the answer lo, lo − 1, or −1 when nothing qualifies? Test on an empty and a single-element input.
  6. Duplicates: Does the caller want any match, the first, or the last? That dictates the comparison.
  7. Search-on-answer: What's the value range? Is feasible(max) guaranteed true (so an answer exists)?
  8. Complexity: O(log n) per probe — or O(n log(max_value)) for search-on-answer. Can I state the cost of one predicate call?

8. First practice problem — LeetCode 704

Binary Search

Given a sorted array nums and an integer target, return the index of target, or −1 if absent. The algorithm must run in O(log n).

Start with the classic closed-interval loop from Section 2. Once it works, the real exercise is re-deriving it with the leftmost-boundary template and confirming both give the same answers on every case you can think of.

Trace these three cases before declaring victory: target smaller than everything, target larger than everything, and target present exactly once. Boundary bugs live in exactly those three places.

Reveal the solution after trying it yourself 
class Solution:
    def search(self, nums: list[int], target: int) -> int:
        lo, hi = 0, len(nums) - 1
        while lo <= hi:
            mid = (lo + hi) // 2
            if nums[mid] == target:
                return mid
            elif nums[mid] < target:
                lo = mid + 1
            else:
                hi = mid - 1
        return -1

Time: O(log n) — the range halves every iteration. Space: O(1).

Follow-up the interviewer will ask: what if the array has duplicates and you want the first occurrence? Switch to the leftmost-boundary template from Pattern 1 — hi = mid instead of mid − 1, and no early return. This is exactly the transition from exact-match thinking to boundary thinking, and making it fluently is the point of this guide.

Practice prompts

  1. Why does the loop condition lo <= hi pair with hi = mid − 1, while lo < hi pairs with hi = mid — what breaks if you swap them?
  2. How many probes would you need for an array of one billion elements — and why is that answer the whole reason binary search exists?
  3. For Koko Eating Bananas, state the predicate and argue in two sentences why it's monotonic.

Try writing the solution from memory, then explain the invariant, the discard rule, and the complexity aloud as you would in an interview.
