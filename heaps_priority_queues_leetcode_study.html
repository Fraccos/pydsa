1. What is a heap?

A binary heap is a complete binary tree — every level full except possibly the last, which fills left to right — where each parent obeys an ordering rule relative to its children:

  • Min-heap: every parent ≤ its children, so the minimum is always at the root.
  • Max-heap: every parent ≥ its children, so the maximum is at the root.
  • Only the root is guaranteed extreme. Nothing else is sorted — finding an arbitrary value still takes O(n).
  • Completeness matters: it's what lets a heap live in a flat array with no pointers.
  • Python's heapq is a min-heap, backed by a plain list. For a max-heap, negate values on the way in and out.

2. Representing a heap in Python

You almost never build node objects. heapq operates on a regular list:

import heapq

nums = [5, 3, 8, 1, 9]
heapq.heapify(nums)          # O(n) — rearranges the list in place into a min-heap

smallest = heapq.heappop(nums)    # 1, O(log n)
heapq.heappush(nums, 2)           # O(log n)
heapq.heappush(nums, 0)
next_smallest = heapq.heappop(nums)   # 0

print(nums[0])               # peek at the min without popping, O(1)

The array layout behind the scenes: for index i, the parent is at (i − 1) // 2, children at 2i + 1 and 2i + 2. Every operation is just swaps in this array — no node objects, no pointers.

How insertion works (sift-up)

heappush(x) does exactly three things: append x at the end of the list (keeping the tree complete), then compare with its parent and swap if out of order, repeating until the parent is ≤ the new node or you reach the root. This is called sift-up, and it walks a single path from a leaf toward the root.

Example — insert 1 into the min-heap [2, 5, 3, 7]:

Cost: the element can only climb from leaf to root — at most ⌊log₂ n⌋ swaps — so insertion is O(log n) worst case, O(1) when the new value is large and stops immediately (the average push does much less work than the worst case). The mirror image is heappop: remove the root, move the last element to the root to keep the tree complete, then sift-down — swap with the smaller child until both children are ≥ — also at most O(log n).

Why heapify is O(n), not O(n log n)

heapify doesn't insert n times. It runs sift-down from the last parent backwards to the root, so each node only has to sink into the part of the tree below it. The trick is that almost all nodes sit near the bottom, where there's almost nowhere to sink:

The sum: total work ≤ Σₕ n·h / 2^(h+1) = (n/2)·Σₕ h/2ʰ = (n/2)·2 = O(n). Intuition for interviews: half the nodes are leaves that cost nothing, a quarter move one step, an eighth move two steps — the expensive root-to-leaf work happens to only one node, and the series converges to a constant times n. That's why building a heap bottom-up beats doing n pushes (O(n log n)).

In interviews, quote it as: "heapify is O(n) because it sifts down level by level, and the number of nodes at each level halves while each level's cost only grows by one — the series sums to O(n)."

The two idioms you'll type in every interview:

# Max-heap by negation
heapq.heappush(heap, -val)
biggest = -heapq.heappop(heap)

# Heap of (key, value) tuples — sorted by key, then value
heapq.heappush(heap, (distance, node))
dist, node = heapq.heappop(heap)

3. Heap vs. sorted array vs. BST

Heap

Fast access to one extreme: O(1) peek, O(log n) push/pop. Everything else is expensive.

Useful for: top-k, scheduling, streaming min/max, Dijkstra.

Sorted array

O(1) access to all extremes, but insertions shift elements: O(n).

Useful for: static data you build once and binary-search often.

Balanced BST

Full ordering: O(log n) insert, delete, and arbitrary search, successor, kth.

Useful for: when you need order and lookups, not just the extreme. See the BST guide.

The interview rule of thumb: when a problem says "keep track of the k largest / k closest / most frequent / next event", you usually don't need full sorting — you need a heap of size k (or a min-heap of the k best seen so far). Sorting the whole input is O(n log n); a size-k heap is O(n log k).

5. Four core interview patterns

Pattern 1 — Top-k with a size-k heap

For the k largest elements, keep a min-heap of size k. The heap's root is the smallest of the "champions" — any new element that can't beat it is discarded in O(1); ones that can, replace it in O(log k).

import heapq

def k_largest(nums, k):
    heap = []
    for num in nums:
        heapq.heappush(heap, num)
        if len(heap) > k:
            heapq.heappop(heap)    # evict the smallest of the k+1
    return heap                    # k largest, unordered internally

Time: O(n log k), space: O(k) — better than sorting (O(n log n), O(n)) whenever k < n. Note the counterintuitive choice: min-heap for the k largest, max-heap for the k smallest. Common problems: Kth Largest Element (215), K Closest Points to Origin (973), Top K Frequent Elements (347, with a hash map counting frequencies first).

Pattern 2 — Merge k sorted lists

Put the head of each list in a min-heap. Pop the global smallest, append it, push that list's next element. The heap always holds exactly one candidate per list.

def merge_k_lists(lists):
    import heapq
    heap = [(node.val, i, node) for i, node in enumerate(lists) if node]
    heapq.heapify(heap)
    dummy = tail = ListNode()

    while heap:
        _, i, node = heapq.heappop(heap)
        tail.next = node
        tail = node
        if node.next:
            heapq.heappush(heap, (node.next.val, i, node.next))
    return dummy.next
The tuple-index trick: tuples compare element by element, and ListNode objects can't be compared. The i breaks ties so Python never falls through to comparing nodes.

Time: O(N log k) for N total nodes across k lists. Common problems: Merge k Sorted Lists (23), Smallest Range from k Lists (632), Ugly Number II (264).

Pattern 3 — Greedy "process the extreme" simulation

Whenever the correct next move is "take the currently largest (or smallest, or most urgent) item, do something to it, and it may come back", a heap encodes the whole loop:

while heap and remaining_moves:
    priority, task = heapq.heappop(heap)
    # process task ...
    if not task.finished:
        heapq.heappush(heap, (new_priority, task))

The greedy part — why taking the extreme is always safe — is the part you must justify aloud. Common problems: Last Stone Weight (1046), Task Scheduler (621), Reorganize String (767), Minimum Cost to Connect Sticks (1167).

Pattern 4 — Two heaps (the median pattern)

A stream's median needs the middle of unordered data. Split the stream into a max-heap holding the smaller half and a min-heap holding the larger half. Then the median is either the top of the larger half or the average of both tops.

class MedianFinder:
    def __init__(self):
        self.small = []   # max-heap (negated): smaller half
        self.large = []   # min-heap: larger half

    def add_num(self, num):
        heapq.heappush(self.small, -num)
        # ensure every element in small <= every element in large
        heapq.heappush(self.large, -heapq.heappop(self.small))
        # keep small equal in size or one ahead
        if len(self.large) > len(self.small):
            heapq.heappush(self.small, -heapq.heappop(self.large))

    def find_median(self):
        if len(self.small) > len(self.large):
            return -self.small[0]
        return (-self.small[0] + self.large[0]) / 2

Time: O(log n) per add, O(1) per query. Hard to invent under pressure — worth memorizing the invariants: (1) max(small) ≤ min(large), (2) sizes differ by at most 1. Common problems: Find Median from Data Stream (295), Sliding Window Median (480), IPO (502).

7. Interview checklist

  1. Direction: k largest → min-heap; k smallest → max-heap. Did I get this backwards?
  2. Key: What is the heap actually ordered by — value, distance, frequency, priority? Tuples need a tiebreaker.
  3. Comparability: Can Python compare my elements? If not, add an index or id to the tuple.
  4. Size: Is the heap bounded (size k, O(n log k)) or unbounded (O(n log n))?
  5. Max-heap: Did I remember heapq is min-only — am I negating on push and pop, and negating peeks?
  6. Greedy proof: Can I justify why taking the extreme now is safe, not just code the loop?
  7. Complexity: Am I quoting O(log n) per operation and O(n) for heapify?
  8. Edge cases: Empty stream, k ≥ n, ties everywhere, all-equal elements, single element.

8. First practice problem — LeetCode 215

Kth Largest Element in an Array

Given an integer array nums and an integer k, return the kth largest element. Note: it is the kth largest in sorted order, not the kth distinct element.

Three honest approaches, in increasing sophistication: sort and index (O(n log n)), heapify and pop k−1 times (O(n + k log n)), or maintain a size-k min-heap (O(n log k)). The size-k heap is the pattern interviewers want to see.

Invariant: after processing each element, the heap contains the k largest elements seen so far, and its root is the smallest of them — i.e., the current kth largest.

import heapq

class Solution:
    def findKthLargest(self, nums: list[int], k: int) -> int:
        heap = []
        for num in nums:
            heapq.heappush(heap, num)
            if len(heap) > k:
                heapq.heappop(heap)
        return heap[0]

Time: O(n log k) — each of the n elements costs at most O(log k) to push and possibly evict. Space: O(k).

Follow-up the interviewer will ask: can you do better than O(n log k)? The expected answer is quickselect — partition around a pivot like quicksort but recurse into only one side, for average O(n) time. Know that it exists and its worst case is O(n²); implementing it is a bonus, not a requirement at mid-level.

Practice prompts

  1. Why a min-heap for the kth largest — what would go wrong with a max-heap of size k?
  2. Why is heap[0] the answer at the end — which invariant guarantees it?
  3. How does this generalize to "k most frequent elements" — what becomes the heap's key?

Try writing the solution from memory, then explain the invariant, the eviction rule, and the complexity aloud as you would in an interview.
